# sealed-agent

The in-VM agent of a Sealed deployment (spec 5.6, INTERFACES 9-15). It releases the stack's keys from the customer's key broker against a TDX quote, unlocks the LUKS2 data disk, writes app secrets to tmpfs, sends attestation evidence, serves `/attest`, meters usage, signs usage and health reports and pays fees on Tempo.

## Boot sequence

1. Read the public config (`SEALED_CONFIG_FILE`) and the booted `app-compose.json` (dstack `GET /Info`). Every endpoint must be `https` (review C-4), except loopback endpoints and dev sim mode. Everything else the agent needs from the composer comes from the measured inline `configs` in that app-compose (the composer doubles `$`, the agent undoes it): `sealed-config` (must equal the config file), `sealed-stack` (sealed-stack/v1: per-app metering, healthcheck, service IPs; sidecar IPs; attest host), `sealed-caddyfile` and `sealed-caddyfile-payment-needed`. The files the composer also mounts (`SEALED_STACK_FILE`, `SEALED_CADDYFILE`, `SEALED_CADDYFILE_PAYMENT_NEEDED`) must hold the same bytes.
2. Ephemeral X25519 key, `GET /v1/nonce`, quote over `sha256("sealed/kb-release/v1" || nonce || pub) || 0^32`, `POST /v1/release`, HPKE-open the payload. The answer must name this stack's stackHash and deploymentId and decrypt under the ephemeral key with `aad = nonce`; anything else is retried with a fresh nonce. Denials are retried every minute.
3. Enclave signer: `HKDF-SHA256(ikm = signerSeed, salt = "sealed/enclave-signer/v1", info = [counter], L = 32)`, first counter giving a valid secp256k1 scalar (frozen by a test vector in `packages/core`).
4. Data disk (below), then every data directory of the stack: the compose's bind sources and sealed-stack/v1 `dataDirs` (host paths under `/mnt/sealed-data`, seen at `SEALED_DATA_DIR`). A volume whose manifest declares `x-sealed-owner` (sealed-stack/v1 `apps[].volumes[].owner`, `"<uid>:<gid>"`) gets that owner on every boot; otherwise a new directory gets the numeric `user` of the first service that mounts it. A symlink or a file in place of a directory fails the boot. All of this happens before the ready flag (brief item 11).
5. Secrets (D-042, composer 1.2 and later): the compose binds the host's `/run/sealed/secrets` (on the CVM's `/run` tmpfs) into the agent only, and binds into each service exactly the files it lists, read-only, from the same host path. Before any key is released the agent reads those binds back and refuses to boot when a service can see another owner's secrets, mounts them writable, binds a host path other than its target, or when they differ from sealed-stack/v1 `secretFiles`. The bind sources are checked too: no service but the agent may bind the secrets root, anything above it (`/`, `/run`, `/run/sealed`, also through `/var/run`), anything below it but one secret file at its own path, or the dstack socket, nor mount a `sealed-secrets-*` volume outside the root (review ws-int-agent 8). After the release it checks that the secrets root is on tmpfs (statfs `0x01021994`), creates each owner directory (0755; a symlink or a file in its place fails the boot) and checks it again (review ws-int-agent 1), and writes exactly the `secretFiles` entries (0444): the released value (a `same_as` secret arrives from the key broker under the referencing app), or an empty file for an optional secret the customer did not set (a missing bind source would stop the container). A missing required one is logged. Only owners other services bind are written, so the gate hash `_gate/GATE_PASSWORD_BCRYPT` is kept in memory only (Caddy holds no secret). Composer 1.1 stacks, with one tmpfs volume per owner, still get their owner directories checked for tmpfs. The payer key and limit go to `sealed-mpp-payer/` only when the stack has the payer. Then `<SEALED_READY_DIR>/ok` (the shared `sealed-ready` tmpfs volume) opens the gate envexec waits for.

   Secret rotation: the agent gets secrets only from a key release, which happens when the VM boots and when the agent container restarts. It writes each file by temp file and rename, while every service binds its own files (D-042), which pins the inode it saw when it started. A secret rotated in the customer's Secret Manager therefore reaches a running service only after that service restarts, and only once a key release has read the new value: restart the deployment (stop and start the VM) to apply a rotation everywhere. An agent container restart alone writes the new value to the path, but services that keep running still see the old one (devnet-e2e, step 11).
6. Check that the run-as user can reach Caddy's admin socket (otherwise the boot fails; there is no root helper), drop to `SEALED_RUN_AS`, read the FeeSplitter per-payment cap, hold the usage read from disk for the ledger rebuild (D-062, below), report ready (`/v1/ready` 200).
7. Evidence bundle (`sealed-evidence/v1`, fresh `nonce2`) to `POST /v1/evidence`, retried with backoff; again every 24 hours (a run that is still retrying is joined, not duplicated).
8. Loops: app health polling (app-hour metering, none while the routes show the payment-needed page), settlement every `settlement.intervalMinutes`, signed health reports. On SIGTERM the agent runs one last settlement (at most 8 s), so the open period is cut, reported and paid before the VM goes away.

## Data disk (D-017)

The host attaches the disk, so the agent trusts nothing on it:

- The LUKS2 volume key and the keyslot passphrase are derived from the broker's `diskKey`: `HKDF-SHA256(ikm = diskKey, salt = "sealed/disk/luks2/v1", info = "volume-key", L = 64)` and `info = "keyslot-passphrase", L = 32`. Format: `luksFormat --type luks2 --cipher aes-xts-plain64 --key-size 512 --volume-key-file /dev/fd/3 --pbkdf pbkdf2 --hash sha256 --key-file -`.
- Before unlocking, `cryptsetup luksDump --dump-json-metadata` must show exactly one luks2 keyslot (aes-xts-plain64 area, 512-bit, pbkdf2/sha256, af luks1/sha256), one crypt segment (aes-xts-plain64, no integrity, no flags), one digest, no tokens and no requirements (so no reencryption).
- Unlock with `--disable-keyring`, then `dmsetup table --showkeys` must show a single crypt target with aes-xts-plain64, exactly the derived volume key, IV offset 0, no integrity options, on the data device's major:minor. Otherwise the mapping is closed and boot fails. A header that did not come from `diskKey` (cipher_null, a keyslot any passphrase opens, a volume key the host knows) can never be mounted. The same check applies to a mapping that already exists after an agent restart.
- "Mounted" means the topmost `/proc/self/mountinfo` entry at the mount point is ext4 from `/dev/mapper/<name>`; the composer's bind mount of the host directory at the same path does not count.
- An established volume whose plaintext shows no filesystem is never formatted: the boot fails and the volume is left untouched (review ws-int-agent 10). Only a volume formatted in this boot gets `mkfs.ext4`.
- Limits: aes-xts has no integrity protection, so the host can still corrupt blocks or roll the disk back to an earlier copy of itself (it cannot read or forge plaintext). A rollback cannot make the agent bill a period twice (D-062, Settlement).

## Password gate (D-044)

Caddy asks `GET /v1/gate?route=<route>` (forward_auth) with the client's headers before it proxies a route whose auth is `gate` (and the non-bearer part of `bearer-passthrough`):

- What counts as the gate's own credential is exactly what Caddy strips (review ws-int-agent 7, C-3): `Basic`, one or more spaces (RFC 7235), canonical padded base64; a cookie named exactly `sealed_gate` right after the separator's whitespace, as Caddy's `(^|;\s*)sealed_gate=` matches. Tabs, unpadded or base64url credentials and `sealed_gate =` are not the gate's.
- `200` for a valid `sealed_gate` cookie, or for `Authorization: Basic` with user `sealed` (sealed-stack/v1 `gate.username`) whose password matches the released bcrypt hash `_gate/GATE_PASSWORD_BCRYPT`. A Basic success adds `Set-Cookie: sealed_gate=v1.<expiresAt>.<session id>.<HMAC-SHA256>; Path=/; Max-Age=43200; HttpOnly; Secure; SameSite=Lax`. The HMAC key is drawn at every boot, so a restart signs everyone out. The cookie is not bound to a route. The answer carries `X-Sealed-Gate: cookie|basic` and, when the request's `Authorization` header holds the gate's own Basic credentials, `X-Sealed-Gate-Strip-Authorization: 1` (the composed Caddyfile removes the gate's own Basic credentials before the app; with the cookie an app's own header, such as a Bearer token, passes untouched).
- `303` instead of `200` for a Basic success on a browser navigation (`X-Forwarded-Method: GET`, `Sec-Fetch-Mode: navigate`): `Location` is the same path and query (`X-Forwarded-Uri`, same-origin paths only) and the answer carries the `Set-Cookie`. forward_auth copies nothing from a 2xx answer onto the client's response but passes other answers through unchanged, so browsers get the cookie whether or not Caddy copies `Set-Cookie` from a 200.
- `401` with `WWW-Authenticate: Basic realm="sealed"` otherwise.
- `503 starting` until the gate hash is released and, for an app with a bootstrap job, until `bootstrap.donePath` exists as a regular file on the data disk (or the job reported done, see the local API). `503 gate not configured` when the released hash is not bcrypt or its cost is above 20.
- `?bearer=1` (review C-6): Caddy's `bearer-passthrough` handle asks only whether the route is open. `200` (`X-Sealed-Gate: bearer`) for a request with `Authorization: Bearer ...` once the keys are released and the app's bootstrap is done, `503 starting` before, `401` without a Bearer token, `403` for a route with no bearer-passthrough handle. The app checks the token. The Caddyfile must send `?bearer=1` from that handle (composer owner).
- `429` with `Retry-After` when a client (X-Forwarded-For from Caddy; IPv6 per /64) failed 10 times in a burst (refills one per 6 s). Clients that failed within the last 10 minutes also share one budget of 30 (one per second); a client without a recent failure never waits for it, so other clients' failures cannot lock out a new login (review ws-int-agent 6). A failed attempt costs a token before bcrypt runs and a success returns it. bcrypt runs at most 8 at a time. Successful Basic checks are remembered for 5 minutes, so clients that keep sending Basic credentials do not pay bcrypt each time.

bcrypt (`$2a$`, `$2b$`, `$2y$`) is implemented in `src/gate/bcrypt.ts` and runs in a worker thread with at most 8 checks in flight. It is tested against golang.org/x/crypto/bcrypt and the OpenWall vectors. Passwords over 72 bytes never match.

## Settlement

Usage is priced as it arrives (`@sealed/core` pricing, remainders carried per app and unit). Reports are cut so no app's fee in a report exceeds `min(defaults cap, FeeSplitter perPaymentCap)`; the onchain cap is read before usage is accepted and again at every settlement. Each settlement rebuilds the ledger (below), closes the period, signs the EIP-712 `UsageReport`, saves it, posts it to `POST /v1/usage` and pays each app's unpaid legs of accepted reports in one Tempo transaction: `approve(FeeSplitter, exact total)` plus one `payFees` per leg.

No double billing after a disk rollback (D-062, review ws-int-agent 2). The host can restore an older copy of the data disk, whose state still holds, as open usage, usage a later report already billed. FeeSplitter dedupes per usageHash only, so cutting it again into a report with another period would pay it twice. So:

- A report is paid only once the platform accepted it (`POST /v1/usage`), so every paid period is among the reports the platform stores. A report that cannot be submitted is not paid (`usage_not_submitted`); settlement is deferred until the platform accepts it, and the deferred fees are paid then (D-073).
- At boot the agent holds the usage it read from disk and cuts nothing until it has read the platform's stored reports (`GET /v1/deployments/:id/usage-reports`, a signed read: EIP-191 by the enclave key over the CJSON of `{at, deploymentId, purpose: "sealed/usage-reports/v1"}` in `x-sealed-at` and `x-sealed-signature`), page by page from the cursor kept in the state. It keeps only reports for this deployment whose EIP-712 signature recovers to its own enclave signer (the digest is recomputed; the platform's usageHash is not trusted), adopts the ones it did not know as submitted and unpaid (the settler then reads `usagePaid` onchain and marks them paid without a transaction), and marks its own ones the platform holds as submitted. A 404 (deployment not registered) means no stored reports. The read is retried in the background until it succeeds and again before every settlement; until the first success in a boot, settlement fails with `ledger_unverified` and an event that would cut a report gets 503.
- `signedThrough` is the end of the latest period signed for this deployment that the agent knows of. No report is ever signed for a period that starts before it (consecutive periods share a boundary). Held usage from a period that a signed report already passes is covered by that report and dropped; held usage from a later period goes back into the open period.
- A report the platform refuses as overlapping a stored one (`409 conflict`, another copy of this disk running at the same time, or a state the rebuild has not seen yet) is void: never paid, never sent again. A 409 that names the report itself counts as accepted.
- A state that belongs to another deployment (a stack upgrade keeps the disk and the signer, D-058, but changes the deploymentId) starts a new ledger and payment status; the budget and bootstrap state carry over. The old deployment's ledger and payment status are kept beside them while it still has usage to report or legs to pay (payments-5, at most 8 earlier deployments): every settlement first rebuilds, cuts and reports its open period and pays its legs under the old deploymentId, and while it is past its grace period the routes stay on the payment-needed page. It is dropped once everything is paid, or when it is Closed onchain (FeeSplitter takes no fee then; the unpaid legs are logged). A boot as a kept deployment (back to an earlier stack) takes back its own ledger and status.
- Residual: the rebuild trusts the platform to return every report it stores. A platform that withholds a paid report while the host rolls the disk back could still bill that period again; the withheld report's usageHash stays visible onchain in `FeesPaid`, with no stored report to match it.

A (report, app) leg is settled only when `usagePaid(deploymentId, usageHash, appId)` is at least the report's fee. FeeSplitter cannot see the report, so the customer can pay a leg first with any amount (contract review logic-F1 b / funds-F-02); a leg paid short stays unpaid and the batch carries `topUpFees(..., total = fee, usageHash)` for it, which pulls only the shortfall, and ends with `approve(FeeSplitter, 0)`. Budgets and the daily cap count the shortfall. A leg someone else paid in full is marked paid without a transaction. A leg opened in another token (`usageToken`) cannot be topped up and is a failure. The customer authorizes the access key with `buildAccessKeyAuthorization` from `@sealed/core` (D-054): `approve` to FeeSplitter and `transferWithMemo` to the treasury on the fee token, `payFees` and `topUpFees` on FeeSplitter, and the escrow precompile's `open`, `topUp`, `requestClose` and `withdraw` for the payer. `test/accessKey.anvil.e2e.test.ts` runs that authorization, both payers, the limit, the scopes and revocation on a local T12 node.

Batches: the oldest legs that fit the daily cap and the payer's balance and access-key limit, at most 10 per transaction; the network fee is estimated for exactly that batch (gas = max(estimate x 1.5 + 50k, 600k + 1.3M per leg)), and the batch shrinks while the estimate reverts or the fee does not fit.

Billing fails closed on the customer's side. Only customer-side failures count toward the grace period (D-073, D-048 billing policy): missing, revoked or expired access keys, the spend limit, the balance, reverted estimates or transactions, a leg opened in another token, an app the registry does not list, and chain read errors (the customer chooses the RPC and controls the firewall, so it can block the RPC). A platform outage never puts a customer on the payment-needed page: what only the platform can do defers settlement instead. While the ledger cannot be rebuilt in this boot, the platform has not accepted a report, or it has not registered the deployment (`ledger_unverified`, `usage_not_submitted`, `deployment_not_registered`; the oracle registers it from the agent's evidence) and nothing else failed, settlement is deferred: `deferredSince` is set in the state and in health reports, no grace period starts, and one a customer-side failure already started stands still and resumes where it stopped. Reports the platform accepted before the outage are still paid; a tick that pays every leg it tries ends a customer-side failure streak, so a customer who fixed their key, limit or balance during the outage leaves the payment-needed page then. Deferred fees are paid once the platform is back. Failures that last `settlement.gracePeriodMinutes` switch Caddy to the measured `Caddyfile.payment-needed` (`POST /load`, `Content-Type: text/caddyfile`); it is re-applied every tick because Caddy restarts with the normal file. A Closed deployment (terminal) switches at once and stays switched. The next successful settlement loads the normal Caddyfile again. Deferrals, not failures: the FeeSplitter daily cap, and legs above a lowered per-payment cap (reported as `overCap`; they cannot be paid at that cap). Legs the last settlement could not pay (over the cap, opened in another token, an app outside the deployment) are counted as `unpayableLegs` and left out of `reserved_for_fees`, so they do not shrink the payer's share for good (review L2). The attest route and the data are never touched.

Caddy creates its admin socket with mode 0660 in the `sealed-caddy-admin` tmpfs (a `2770` volume owned by 10001:10001, so the socket's group is 10001; brief item 15; sealed-stack/v1 `caddy.adminSocketMode` and `adminSocketOwner`), so the agent loads the two measured Caddyfiles over it directly after dropping to 10001:10001 and keeps no root process (review ws-int-agent 9). There is no root helper: when the run-as user cannot reach the socket as the stack describes it, the boot fails before the ready flag, since the payment-needed switch would otherwise never work.

Shared spend budget (D-048): fee settlement and sealed-mpp-payer draw on one limit. In `access-key` mode it is the customer's onchain authorization: the agent reads the key's remaining fee-token limit and period end (`getRemainingLimit`, at boot, after every settlement, and when a reservation finds the reading over 60 s old), and the payer gets at most `remaining - spent since the read started - open reservations - reserved_for_fees`. Any amount and any period (day, week, month) is followed as authorized; `settlement.spendLimitPerDay` is not used. Before the first read, and for a missing, revoked or expired key, the payer gets nothing. In `enclave-account` mode, and for a key without limits, the limit is `settlement.spendLimitPerDay` per UTC day: `limit - fees spent - payer spent - open reservations - reserved_for_fees`. In `enclave-account` mode nothing onchain limits fee settlement, so the agent caps it at `limit - spent - open reservations` (review I6); fees beyond that fail with `spend_limit` like an access-key limit would.

`reserved_for_fees` covers the whole window (the onchain period, else the UTC day): unpaid legs, the open period's fees, app-hours of heartbeat apps until the window ends (none while the payment-needed page is shown, when no app-hour is recorded), what earlier deployments on the disk still owe, a network fee allowance per app transaction of the next settlement, and the later settlements' transactions at twice the last network fee seen (0.01 USD each until one is seen). The allowance is 0.01 USD on mainnet. Off mainnet every settlement transaction has a gas limit of at least 5M (`LOCAL_MIN_GAS`, headroom on local nodes) and the settler sends one only when its own reserve for that gas fits the limit, so the allowance there is that reserve at the highest local gas price (TIP-1067's base fee cap of 1.2e10 attodollars per gas plus anvil's 1e9 priority fee, doubled like every fee reserve): 0.13 USD. With 0.01 USD the payer could take what a local settlement then needs, which would fail with `spend_limit` although the limit covered the fees. A stack whose app-hours do not fit the limit leaves the payer nothing.

Nothing that may have left the limit is dropped: each payment counts its fees plus the network fee it paid; a reverted one counts its network fee; one whose broadcast or receipt was lost (the agent signs locally, so it knows the hash) counts its fees plus the fee reserve until its receipt shows, looked up at every settlement and given up after 6 hours with the count kept. Open reservations survive the window roll, and what they spent counts in the window they are released in. A reservation not released within 15 minutes counts as spent until a late release corrects it. A reservation is saved to the state file on the encrypted disk before its id is returned (503 if the save fails). A `purpose: "recovery"` reservation (the payer's requestClose or withdraw of an orphaned channel) may go past `reserved_for_fees` by at most one network fee allowance per transaction and five per window, never past the limit itself (payments-8).

- `access-key` mode signs with `Account.fromSecp256k1(enclaveKey, { access: customer })`, so FeeSplitter sees the customer as `msg.sender`.
- `enclave-account` mode pays from the enclave signer's own balance of the fee token.

Every payment, approval and network fee uses the config's `feeToken` (USDC.e on mainnet, D-035); nothing in the agent assumes pathUSD.

## Health report body

`POST /v1/health` `{"deploymentId","signature","body"}`, EIP-191 by the enclave signer over CJSON of:

```json
{"at":1800000000,
 "apps":{"crm":"healthy"},
 "egress":{"since":1799999000,"allowed":{"host:port":3},"blocked":{"host:port":1}},
 "payments":{"mode":"access-key","paymentNeeded":false,"failingSince":null,"deferredSince":null,"lastPaidAt":null,"lastAttemptAt":null,"lastOutcome":"settled",
             "metered":"200833","unpaid":"0","overCap":0,
             "budget_limit":"2000000","budget_source":"onchain","budget_fees":"202833","budget_payer":"40000","budget_reserved":"0",
             "budget_reservedForFees":"10200","budget_payerAvailable":"1746967","budget_windowEnd":"1800014400",
             "budget_onchainRemaining":"1797167","budget_onchainReadAt":"1800000000",
             "mpp_debited":"1200","mpp_budget":"2000000","mpp_charges":3,"mpp_relayAttested":true}}
```

`mpp_*` are the payer's own counters from `POST /v1/spend` (its SpendReport as runtime/mpp-payer builds it, nested `counters`, `relay` and `recovery` flattened; `recovery` becomes `mpp_recoveryRequestCloses`, `mpp_recoveryWithdrawals`, `mpp_recovered`, `mpp_recoveryFailures`, `mpp_recoveryDeferred` and `mpp_recoveryDeferredAmount`); `previous_deployments`, `previous_unpaid` and `previous_paymentNeeded` appear while earlier deployments on the disk still owe fees, and `paymentNeeded` is what the routes show; `budget_*` is the shared budget above (`budget_source` is `onchain`, `config` or `unread`; `budget_pendingTxs` appears while a payment's receipt is outstanding). `deferredSince` is set while settlement waits for the platform (D-073); `unpayableLegs` counts the legs the last settlement could not pay; `ledger_verified`, `ledger_verifiedAt` and `ledger_signedThrough` show the D-062 rebuild. At most 64 payment fields are sent (the api's limit).

Egress keys must look like `host:port` (lowercase, optional `*.`), at most 50 per map, largest counts first.

D-065: an app can modulate counts (how often it is blocked, how much it spends through the payer) to pass a few bits per report to the platform (review ws-int-agent 3). Every count (a number) and amount (a decimal string) in the report is rounded down to two significant figures (`roundDownSignificant` in `@sealed/core`: 0 to 99 stay, 123 becomes 120, 98765 becomes 98000), egress counts before the 50 largest are picked. Sent exactly: timestamps, limits (`budget_limit`, `mpp_limit`, `mpp_budget`), and totals the platform holds exactly anyway (`metered` and `unpaid` from the signed usage reports, `budget_fees` and `budget_onchainRemaining` from the chain). Usage quantities in signed usage reports stay exact, because billing needs them. App health states are not counts and are sent as they are.

When the platform answers a health report with `reattest: true` (the customer asked for a re-attestation, D-068), the agent sends fresh evidence at once.

## Dev simulator

```
node dist/sim.js --app-compose app-compose.json --socket /tmp/dstack.sock   # or --port 8090
SEALED_DEV_SIM=1 DSTACK_SIMULATOR_ENDPOINT=/tmp/dstack.sock SEALED_DISK_MODE=dir node dist/main.js
```

Quotes are `SEALEDSIM1 || CJSON(...)` with the fixed sim measurements (INTERFACES 15) and an RTMR3 replayed from the exact dstack event sequence for the given compose. Production verifiers reject them.

## Tests

`pnpm --filter @sealed/agent test`. `test/catalog.e2e.test.ts` runs the real composer (`go run ./runtime/composer/cmd/sealed-compose compose --fill-release-ids --allow-missing-sbom`) on the catalog apps, boots the agent on that app-compose and verifies its evidence with the verifier library in simulator mode (`test/tools/verify-evidence.go`); it needs Go and is required when `CI` or `SEALED_REQUIRE_CHAIN_TESTS=1` is set. `test/golden.test.ts` boots the agent on the composer's golden app-compose (`test/fixtures/composer-golden`, copied from `runtime/composer/testdata/golden`), and `test/golden12.test.ts` on the composer 1.2.0 golden stack (`test/fixtures/composer-golden-1.2`, from ws/int-composer) with the tmpfs checks on and only the secrets root on tmpfs. `test/rollback.e2e.test.ts` is the D-062 regression: it rolls the data disk back to an older copy, boots again, and checks that no leg is billed twice (also with the platform down at boot, and with two copies of the disk running at once). The chain tests start `anvil --network tempo --hardfork T12` (mainnet's hardfork, Foundry 1.8.6, D-053) and deploy the contracts from `contracts/out` (or `SEALED_CONTRACTS_DIR`); they are skipped when anvil or the contracts are missing, and fail instead with `SEALED_REQUIRE_CHAIN_TESTS=1` (CI), which also requires `pnpm -r build` for the simulator CLI test.

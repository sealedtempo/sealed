# Sealed interfaces (v1)

This file is the contract between components. Every format, hash and endpoint that crosses a component boundary is defined here. If code and this file disagree, fix one of them in the same commit. Component READMEs (`runtime/composer/README.md`, `runtime/agent/README.md`, `runtime/egress/README.md`, `verifier/README.md`, `key-broker/README.md`, `cli/README.md`) hold the finer detail; where they go further than this file, they must not contradict it.

Conventions:
- `0x` hex for all byte values in JSON. Lowercase hex. Addresses are EIP-55 checksummed in UI only; lowercase in hashes and JSON.
- `sha256` for hashes over offchain artifacts (quote, event log, config, compose, bundles). `keccak256` for onchain ids.
- `||` is byte concatenation. Integers in byte strings are big-endian (`uint64be` is 8 bytes).
- Times are unix seconds (uint64).
- Money is in FEE_TOKEN base units as decimal strings in JSON, `uint256` onchain. FEE_TOKEN is the config's `feeToken`: USDC.e `0x20c000000000000000000000b9537d11c60e8b50` on Tempo mainnet (D-035), 6 decimals. Local Tempo nodes fund pathUSD (`0x20c0000000000000000000000000000000000000`), which tests use.

## 1. Canonical JSON (CJSON)

Used for config, compose, egress policy, event log, stack info and release plaintext hashing.

- RFC 8785 (JCS) restricted profile: object keys sorted by byte order (keys must be ASCII), no insignificant whitespace, UTF-8, no trailing newline.
- Numbers: integers only, within +/- 2^53. No floats anywhere in hashed documents (use integer base units, basis points, seconds).
- Strings: JSON escapes only for `"`, `\`, and control characters (`\b \f \n \r \t`, others as `\u00XX`). No HTML escaping (Go: `SetEscapeHTML(false)`).
- Multi-line strings embedded in JSON use LF only.
- Implementations: Go `runtime/composer/cjson` (the only Go implementation: the composer, verifier, egress, key broker and CLI all use it, D-006, D-040), TS `@sealed/core` (`canonicalize`, `parseCJSON`). Both run the shared vectors in `runtime/composer/testdata/cjson/*.json`.

## 2. Ids and hashes

| name | formula |
|---|---|
| appId | `keccak256(bytes(slug))` |
| releaseId | `keccak256(abi.encode(appId, version /*string*/, bundleHash))`, where version is the manifest's `release_version`, else `upstream.version` |
| deploymentId | `keccak256(abi.encode(customer /*address*/, stackHash, salt /*bytes32*/))` |
| imageId | `keccak256(abi.encode(name /*string*/, version /*string*/, measurementsHash))` (computed offchain; contracts accept any unique non-zero id) |
| measurementsHash | `keccak256(mrtd \|\| rtmr0 \|\| rtmr1 \|\| rtmr2)`, each exactly 48 bytes |
| bundleHash | `sha256(bundle.tar)` (section 7) |
| egressPolicyHash | `sha256(CJSON(egress.yaml parsed))` |
| sbomHash | `sha256(CJSON({"<image name>": "0x<sha256 hex of sbom/<image>.spdx.json>", ...}))`, `{}` when a bundle has no SBOMs |
| configHash | `sha256(CJSON(normalized public config))` (section 5) |
| stackHash | dstack compose hash: `sha256(app-compose.json bytes)` (section 6) |
| quoteHash | `sha256(raw quote bytes)`: exactly the signed quote (header, TD body, signature data length and signature data). dstack's GetQuote returns it zero-padded to 8000 bytes; the padding is cut first (`trimQuote` in @sealed/core, `attest.TrimQuote`) and verifiers and the key broker refuse any trailing byte, and a PCK certificate chain not in canonical PEM form, as `quote_invalid`. The two ECDSA signatures stay malleable ((r, n-s) also verifies), so quoteHash is not unique per attestation; freshness rests on report_data |
| eventLogHash | `sha256(CJSON(event log array))` |
| usageHash | EIP-712 digest of the UsageReport (section 4.2) |

## 3. report_data constructions (TDX, 64 bytes)

All three are `sha256(tag || fields)` followed by 32 zero bytes. The ASCII tag gives domain separation between the three uses (D-010).

| use | formula |
|---|---|
| key release | `sha256("sealed/kb-release/v1" \|\| nonce[32] \|\| ephemeralPub[32])` |
| evidence | `sha256("sealed/evidence/v1" \|\| stackHash[32] \|\| configHash[32] \|\| enclaveSigner[20] \|\| nonce2[32] \|\| uint64be(attestedAt))` (D-047) |
| live attest | `sha256("sealed/attest/v1" \|\| nonce[32] \|\| tlsPubKeyHash[32] \|\| enclaveSigner[20])` where `tlsPubKeyHash = sha256(DER SubjectPublicKeyInfo of the serving TLS cert)` |

`nonce2` for evidence: 32 random bytes generated by the agent, included in the bundle. It makes each evidence quote unique. `attestedAt` is bound in report_data (D-047), so the evidence acceptance window (15 minutes, at most 5 minutes in the future) holds before a deployment is registered too. The agent takes `attestedAt` before it asks for the quote. The key-release `nonce` comes from the key broker (`GET /v1/nonce`, section 9); the live-attest `nonce` is the caller's (`GET /attest?nonce=0x<32 bytes>`, section 11, 400 for anything else). Go builders: `verifier/attest` `KeyReleaseReportData`, `EvidenceReportData`, `LiveAttestReportData`; TS: `@sealed/core` `kbReleaseReportData`, `evidenceReportData`, `attestReportData`.

Evidence vector (`packages/core/test/reportData.test.ts`, `verifier/attest`): stackHash 32 x `0x01`, configHash 32 x `0x02`, enclaveSigner 20 x `0x03`, nonce2 32 x `0x04`, attestedAt `1730000000` give `ecf4a53654152e242b80948f7c0657f5821a0406eb2a8291c5c0927696178ed3` followed by 32 zero bytes.

## 4. EIP-712

### 4.1 Deployment records (DeploymentRegistry)

Domain: `{name: "Sealed DeploymentRegistry", version: "1", chainId: 4217, verifyingContract: DeploymentRegistry}`.

```
Record(bytes32 deploymentId,address customer,bytes32 stackHash,bytes32 imageId,bytes32 quoteHash,bytes32 eventLogHash,bytes32 configHash,address enclaveSigner,uint64 attestedAt)
Heartbeat(bytes32 deploymentId,bytes32 quoteHash,uint64 attestedAt)
```

`DeploymentRegistry.recordDigest(Record)` and `heartbeatDigest(deploymentId, quoteHash, attestedAt)` are public views returning the EIP-712 digests. `IAttestationVerifier.verify(digest, evidence)` receives one of these digests.

Method 1 (ORACLE_SIG_V1) evidence: `abi.encode(bytes signature)` where signature is a 65-byte ECDSA signature over the digest by an allowed oracle signer (v is 27 or 28). Method 2 (ZK_DCAP_V1) is reserved; see ZK_UPGRADE.md for its evidence layout.

### 4.2 Usage reports (signed by the enclave signer)

Domain: `{name: "Sealed Usage", version: "1", chainId: 4217, verifyingContract: FeeSplitter}`.

```
UsageItem(bytes32 appId,uint8 unit,uint256 quantity,uint256 fee)
UsageReport(bytes32 deploymentId,uint64 periodStart,uint64 periodEnd,UsageItem[] items)
```

Units: `1 = tokens` (count), `2 = pages` (successful requests), `3 = app_hour` (quantity in seconds, priced per hour). `fee` is in FEE_TOKEN base units. The report digest is the `usageHash` passed to `FeeSplitter.payFees` for every app in that report. A leg `(deploymentId, usageHash, appId)` counts as paid only when the `FeesPaid` amounts for it sum to the report's fee (D-034); a short leg is completed with `topUpFees`.

Pricing (from `config/defaults.yaml`, 6 decimals): tokens `fee = floor(q * 200000 / 1_000_000)` (0.20 USD per 1M); pages `floor(q * 200000 / 1000)` (0.20 USD per 1k); app_hour `floor(q * price_units / 3600)`. Fractional remainders carry into the next period per app. No fee in a report exceeds `min(defaults cap, FeeSplitter perPaymentCap)`; the agent cuts reports to fit.

## 5. Public deployment config (`sealed-config/v1`)

Never contains secrets. Measured: it is an input to the composer, so it is covered by stackHash, and `configHash` binds it in the evidence quote.

```json
{
  "schema": "sealed-config/v1",
  "chainId": 4217,
  "customer": "0x…",
  "salt": "0x…32 bytes",
  "imageId": "0x…",
  "composerVersion": "1.4.0",
  "apps": [ { "id": "llm-gateway", "releaseId": "0x…" } ],
  "hostnames": { "scheme": "sslip", "ip": "34.1.2.3" },
  "egressAdditions": { "scraper": ["example.com:443"] },
  "allowedVpcRanges": [],
  "debug": false,
  "endpoints": {
    "keyBroker": "https://sealed-key-broker-xyz.a.run.app",
    "platformApi": "https://api.example",
    "tempoRpc": "https://rpc.tempo.xyz",
    "relay": "https://attest.34-9-8-7.sslip.io",
    "relayAttest": "https://attest.34-9-8-7.sslip.io/attest"
  },
  "contracts": { "platformRegistry": "0x…", "appRegistry": "0x…", "deploymentRegistry": "0x…", "feeSplitter": "0x…" },
  "feeToken": "0x20c000000000000000000000b9537d11c60e8b50",
  "settlement": { "mode": "access-key", "intervalMinutes": 60, "gracePeriodMinutes": 1440, "spendLimitPerDay": "2000000" },
  "relayOwner": "0x…"
}
```

- `composerVersion` must equal the composer's `Version` (`1.4.0`, `sealed-compose version` prints it); a composer refuses configs of any other version, so the key broker, verifierd and the CLI recompute only stacks of their own composer version.
- Parsing is strict: unknown fields, keys in another case, duplicate keys, floats and mixed-case hex are refused. Bounds: at most 128 KiB of JSON, 16 apps, 64 egress additions per app and 256 in total, 32 VPC ranges.
- `apps` sorted by `id`, unique. `egressAdditions` entries are `host:port`, host may start with `*.` for one-label wildcards; only for apps in the stack whose egress policy has `customer_additions_allowed: true`. IPv4 literals must be public unicast; RFC 1918 literals are accepted only inside `allowedVpcRanges`.
- `allowedVpcRanges` lie wholly in RFC 1918 space and overlap neither of the VM ranges (`composer.VMRanges`): `172.30.0.0/16`, which holds `apps`, the app networks 172.30.1.0/24 to 172.30.16.0/24 and the `verifier` network 172.30.250.0/24, and `172.31.0.0/24` (`edge`).
- `debug` (boolean, default `false`): container logs use the `local` driver when true, else none. It is part of configHash, so the customer approves it.
- Normalization: absent `egressAdditions`, `allowedVpcRanges` and `debug` become `{}`, `[]` and `false`, and the canonical form always carries them. configHash is over that normalized form (Go `Config.CanonicalJSON`; the TS twin `sealedConfigSchema` applies the same defaults, but it is a looser parser: only the Go composer validates). The composer writes the normalized config into the stack, so the VM, the evidence bundle and the platform's stored config all carry it.
- Endpoint URLs are `https` without credentials (since composer 1.3.0, review C-4); the port defaults to 443 and the host becomes a `host:port` egress entry, so loopback and other non-public IP literals are refused. `endpoints.relayAttest` is exactly `https://<relay attest host>/attest`, without query or fragment (review C-11). `relayOwner`, `endpoints.relay` and `endpoints.relayAttest` are required when `llm-gateway` is in the stack; then `endpoints.relay` must be exactly the origin of `endpoints.relayAttest` (scheme and host, no path, no trailing slash), because the relay is served on its deployment's attest host (D-045) and the payer pins relay requests to the attested TLS key.
- `hostnames.scheme` is `sslip` (`<route>.<ip-with-dashes>.sslip.io`) or `custom` with `"domains": {"<route>": "llm.example.com", "attest": "...", ...}`: a domain for every route in the stack plus `attest`, none for routes outside it, none for a route served on the attest host.
- `settlement.mode` is `access-key` or `enclave-account`.
- deploymentId is derived, not stored: `keccak256(abi.encode(customer, stackHash, salt))`.

## 6. Stack composition

Inputs: public config, release bundles (by releaseId, fetched by the release asset URL rule and checked against the onchain bundleHash, section 7), composer version. Output: `app-compose.json` (dstack) whose sha256 is stackHash.

- `docker_compose_file` is the composed compose document serialized as CJSON (compose accepts JSON); project name `sealed`. Every `$` in measured text is written as `$$`, so compose interpolation never reads host environment.
- All images by digest, exactly `<registry>/<name>@sha256:…` with the registry of `runtime/composer/runtime-images.json` (`ghcr.io/sealedtempo`, equal to `config/defaults.yaml` `catalog.registry`). Tags are rejected. Zero digests (images not built yet) compose but are listed in the result's `unbuilt`; release lint refuses them.
- Secrets never appear. Apps read them from `/run/sealed/secrets/<appId>/<NAME>` (section 14) and wait for `/run/sealed/ready/ok`.
- The composer writes the public config, the stack info, the egress config and the Caddyfiles into the compose as inline `configs` content, so they are measured.
- Networks (D-041), all bridges with IPv6 off:

| network | subnet | members |
|---|---|---|
| `apps` | `172.30.0.0/24`, internal | the sidecars and each app's primary service (alias `<appId>`) |
| `edge` | `172.31.0.0/24`, inter-container traffic off | sealed-egress `.2`, caddy `.4` (publishes 80 and 443) |
| `app-<appId>` | `172.30.<n>.0/24`, internal, n = 1..16 in sorted app order | every service of the app, sealed-egress `.2`, sealed-agent `.3` |
| `verifier` | `172.30.250.0/24`, internal, only when llm-gateway is in the stack (D-061) | sealed-egress `.2`, sealed-mpp-payer `.5`, sealed-verifierd `.6` |

- Bridge names: `sealed-apps`, `sealed-edge`, `sealed-app<n>`, `sealed-verifier` (the host rules match `sealed-+`, section 15).
- Fixed addresses on `apps`: sealed-egress `.2`, sealed-agent `.3`, caddy `.4`, sealed-mpp-payer `.5` (only when llm-gateway is in the stack), app primaries from `.16` in app order. sealed-verifierd is on the `verifier` network only (`172.30.250.6`), so no app primary can call it and use its egress allowlist (D-061, review V-1). On `app-<appId>`: the primary `.16`, the other services from `.17` in name order. A service of one app reaches another app's service only when both are primaries on `apps` (for example coding-agent to `llm-gateway`, llm-gateway to `sealed-mpp-payer`). The gate is not a boundary between primaries (review C-2): a primary must authenticate its callers itself or accept only Caddy's address.
- Every container on two or more networks gets `sysctls: {"net.ipv4.ip_forward": "0"}` (D-064), so sealed-egress, Caddy, the agent, the payer and the primaries never route packets between their networks.
- No service that mounts an inline config is `read_only` (D-063): compose copies `content` configs into the container's root filesystem at create time and refuses a read-only service with one. `Compose` refuses that combination.
- app-compose.json (dstack v0.6.1, `manifest_version` 2) is exactly this object serialized as CJSON, no trailing newline, at most 50 MiB:
  `{"allowed_envs":[],"docker_compose_file":"<CJSON compose>","gateway_enabled":false,"key_provider":"tpm","key_provider_id":"","kms_enabled":false,"local_key_provider_enabled":false,"manifest_version":2,"name":"sealed-<first 8 hex of configHash>","no_instance_id":false,"pre_launch_script":"<host rules, section 15>","public_logs":false,"public_sysinfo":false,"public_tcbinfo":true,"runner":"docker-compose","secure_time":false,"storage_fs":"ext4"}`.
  No `init_script` or `features`. Unmeasured host inputs (`.sys-config.json`, `.instance_info`, `app_id`) never drive any decision. `secure_time` stays false (D-073): the bootstrap firewall allows egress on 443 and 53 only, so NTS cannot work; attestedAt is bound in report_data and checked against the oracle's clock and the block time instead.
- RTMR3 (event log v1): each event digest is `sha384(le32(0x08000001) || ":" || name || ":" || payload)`; `RTMR3 = sha384(RTMR3 || digest)` from 48 zero bytes. Verifiers require exactly this sequence and reject unknown events: `system-preparing`, `app-id`(20 bytes), `compose-hash`(32, equals stackHash), `gpu-policy-hash`(32, `44136fa3...aff8a` for no policy), `instance-id`(20), `boot-mr-done`, `key-provider`(`{"name":"tpm","id":""}`), `storage-fs`(`ext4`), `storage-encrypted`(`1`), `system-ready`. Golden vectors: `runtime/composer/testdata/dstack/`.
- Determinism: any change to composed bytes (composer code, `runtime-images.json`, the Caddy template, the host rules) needs a new composer version, because approved stacks pin the old bytes. `runtime/composer/testdata/golden/` pins the fixture stack (composer 1.4.0: stackHash `0x8d592d7609ef9381029923b9c2d290b035f23762daee36e929f4941279d29c3e`); consumers that copy the goldens (`runtime/agent/test/fixtures/composer-golden`) copy them again, and an agent test fails when the copy differs by one byte.

## 7. Release bundle and release assets

Deterministic tar (POSIX ustar written by the composer's own encoder, entries sorted by path with explicit parent directories, mtime 0, uid/gid 0, uname/gname empty, mode 0644 files, 0755 dirs, LF endings in text files, no record padding, at most 64 MiB). Only the canonical form loads, so one bundleHash names exactly one content:

```
manifest.yaml
compose.fragment.yaml
egress.yaml
LICENSES/<files>          (the app's LICENSE-NOTICE and LICENSES/)
sbom/<image-name>.spdx.json
scan/<image-name>.json
```

At build time every `images[].ref` in the bundled manifest is set to `<catalog.registry>/<name>@<digest>`. `sealed release build <app>` and release CI (`catalog/tools/release bundle`) both build with `composer.BuildBundle` and reproduce bundleHash byte for byte; the composer reads only manifest.yaml, compose.fragment.yaml and egress.yaml.

Egress policy (`egress.yaml`):
```yaml
version: 1
default_allow: ["api.example.com:443"]   # at most 256 entries
customer_additions_allowed: true
notes: "why each entry exists"
```

Release assets (D-046), one GitHub Release per app version under `catalog.release_asset_base` (`https://github.com/sealedtempo/sealed/releases/download`). `version` is the version hashed into releaseId, used literally in releaseId and in the asset names, and must match `^[0-9A-Za-z][0-9A-Za-z._-]{0,63}$` (GitHub renames other characters, `+` included). The tag names `tagVersion` (`composer.TagVersion`): the version without one leading `v` or `V` that a digit follows, so the tag's own `v` is never doubled (coding-agent `v1.58.2` is tagged `coding-agent-v1.58.2`, with the asset `coding-agent-v1.58.2.bundle.tar`; crm `10.0.11` is tagged `crm-v10.0.11`). A leading `v` or `V` before anything else (`vnext`) is refused by lint, release CI and every fetcher (`composer.CheckReleaseVersion`). Two versions that differ only by that letter (`1.2.3` and `v1.2.3`) share one tag, so an app can release only one of them.

| asset | URL or name |
|---|---|
| tag | `<appId>-v<tagVersion>` |
| bundle | `<base>/<appId>-v<tagVersion>/<appId>-<version>.bundle.tar` |
| cosign signature, certificate, Sigstore bundle | the bundle URL plus `.sig`, `.crt`, `.sigstore.json` |
| SLSA provenance | the bundle URL plus `.intoto.jsonl` |
| SBOM and scan of an image | `sbom.<image>.spdx.json`, `scan.<image>.json` in the same release (the bundle's `sbom/` and `scan/` files; asset names cannot contain `/`) |
| release summary | `<appId>-<version>.release.json` (`sealed-release/v1`, for the api and console) |

The rule is implemented once, `runtime/composer` `NewReleaseAssets`, `ReleaseTag`, `TagVersion`, `BundleAssetName`, `SBOMAssetName` (the private api's `assetUrls` and the devnet keep tested copies); release CI names, the key broker, sealed-verifierd (`verifier/bundles`) and the CLI use it. Fetchers follow redirects, accept a bundle only when its sha256 equals the onchain bundleHash (else `bundle_hash_mismatch`), load it in canonical form and cache it by hash. Onchain `signatureURI` is the `.sig` URL and `provenanceURI` the `.intoto.jsonl` URL.

## 8. Evidence bundle (`sealed-evidence/v1`)

Produced by sealed-agent, sent to `POST /v1/evidence`, downloadable from the console and `GET /v1/deployments/:id/evidence`, consumed by `sealed verify`.

```json
{
  "schema": "sealed-evidence/v1",
  "chainId": 4217,
  "contracts": { "platformRegistry": "0x…", "appRegistry": "0x…", "deploymentRegistry": "0x…" },
  "deploymentId": "0x…",
  "customer": "0x…",
  "imageId": "0x…",
  "releaseIds": ["0x…"],
  "config": { "…": "normalized public config, section 5" },
  "configHash": "0x…",
  "appCompose": "<exact app-compose.json string>",
  "stackHash": "0x…",
  "enclaveSigner": "0x…",
  "nonce2": "0x…",
  "attestedAt": 1730000000,
  "quote": "0x…",
  "quoteHash": "0x…",
  "eventLog": [ { "imr": 3, "event_type": 134217729, "digest": "…", "event": "compose-hash", "event_payload": "…" } ],
  "eventLogHash": "0x…",
  "runtime": "dstack",
  "record": { "txHash": "0x…", "method": 1 }
}
```

- `config` is the normalized config the VM mounts at `/etc/sealed/config.json`, so `sha256(CJSON(config)) = configHash`.
- `quote` is exactly the signed quote: dstack on GCP returns it zero padded in an 8000-byte buffer (4935 signed bytes on C3), and verifiers refuse trailing bytes, so producers trim to the signed length (D-052; the agent's `getQuote` uses `trimQuote`).
- report_data is the evidence construction of section 3, with `attestedAt` bound (D-047).
- `runtime` is `dstack`; `fallback` is reserved in the schema and never produced.
- `record` is added by the platform after registration and is not covered by any hash.
- Verification checks and their order are listed in `verifier/README.md` (`bundle`, `chain`, `quote_hash`, `quote`, `td_attributes`, `image_measurements`, `image_approved`, `event_log_hash`, `rtmr3`, `compose_hash`, `config_hash`, `config_binding`, `deployment_id`, `report_data`, `freshness`, `releases_active`, `stack_recompute`, `stack_approved`, `approval_releases`, `onchain_record`, plus `expected_customer` and `expected_apps` when requested; live mode adds `live_fetch` and `tls_binding`). `chain` also requires `config.contracts.feeSplitter` to equal the verifier's FeeSplitter when it knows one, and pins every read to the head block, whose timestamp must be within `MaxChainHeadAge` (default 60 s, at most 300 s) of the verifier's clock in either direction (D-060); a stale head fails `chain` with `data.reason: "chain_stale"` (a head that far in the future with `"chain_clock_skew"`), and the data always carries `blockNumber`, `headTimestamp`, `headLagSeconds` and `maxHeadLagSeconds`. `td_attributes` checks the rule of section 9 (no debug or migratable bit, `SEPT_VE_DISABLE` set, no reserved bit) and reports `tdAttributes` and `xfam` in its data; XFAM is not pinned yet (D-070).

Verifier report (`verify.Report`, JSON): `{"ok","simulated","mode":"evidence"|"live"|"live_submitted","deploymentId"?,"stackHash"?,"recordDigest"?,"blockNumber"?,"verifiedAt","config"?,"checks":[{"name","ok","detail","data"?}]}`. `ok` is true only when there is at least one check and every check passed, and never for a simulated quote the verification did not opt in to (`Options.AcceptSimulated`). `config` is present when the config parsed: `{"debug","endpoints":{"keyBroker","platformApi","tempoRpc","relay","relayAttest"},"egressAdditions"?,"allowedVpcRanges"?,"relayOwner"?}`, with URLs stripped of credentials, query and fragment and the Tempo RPC shown as scheme and host only.

## 9. Key broker API

Runs on Cloud Run in the customer's project (spec 5.7, `key-broker/`), deployed by the customer's bootstrap (section 16), max instances 1, listening on `$PORT` (8080). `key-broker/README.md` has the operator detail.

`GET /v1/nonce` -> `{"nonce":"0x…32 bytes","expiresAt":1730000300}`. Single use, 5 minute lifetime. The store is bounded (100,000 live nonces, oldest evicted first, D-066) and lives in memory; a journal file can keep it across restarts, which helps only on durable storage. `GET /healthz` -> `{"status":"ok"}`.

`POST /v1/release`, strict JSON (unknown, duplicate or differently cased keys are refused):
```json
{ "nonce": "0x…", "ephemeralPub": "0x…32 bytes X25519", "quote": "0x…", "eventLog": [], "config": {}, "appCompose": "…", "releaseIds": ["0x…"], "imageId": "0x…" }
```

Limits before any check (D-066): per client address (the last `X-Forwarded-For` hop, which Cloud Run appends) 2 release requests per second with a burst of 20, and four times that for nonces, else 429 `rate_limited`; the body is read with a 10 s deadline and at most 2 MiB (413 `bad_request` beyond), before any release slot; at most 4 bodies are parsed at a time; a release slot (8 by default) is taken only after the nonce is consumed and the body validated, else 429 `rate_limited`. Requests that fail before that point are logged truncated and in the background.

Checks, in order (`key-broker/release.go`); the nonce is consumed before any other field is looked at, so every attempt burns it, every chain read is pinned to one block, and each check is logged with its data:

| check | denial reason |
|---|---|
| `nonce`: issued here, unused, unexpired | `bad_nonce` |
| `request`: well formed, sizes bounded | 400 `bad_request` |
| `quote`: verifies with Intel PCS collateral (the PCK chain must end at the Intel SGX Root CA); a request without a TDX quote, a quote with trailing bytes and a simulated quote on a production build are refused | `quote_invalid`; 503 `unavailable` when PCS or its cache cannot serve the collateral |
| `quote`: TCB status allowed (`UpToDate`, `SWHardeningNeeded` by default) | `tcb_status` |
| `report_data`: equals the key-release construction | `report_data_mismatch` |
| `chain`: the RPC serves the configured chain (4217 on mainnet) and its head block is at most 60 s from the broker's clock in either direction (D-060); every later read is pinned to that block | 503 `chain_stale` (recorded as a denial, `Retry-After: 5`) |
| `image`: `getImage(imageId)` exists | `image_not_approved` |

The broker's own FeeSplitter and fee token default to mainnet's; the bootstrap sets `SEALED_FEE_SPLITTER` and `SEALED_FEE_TOKEN` when the registries are on another chain, and `SEALED_ALLOWED_IMAGES` (comma-separated 0x imageIds) when the customer chose an image allowlist (section 16).

200 response: `{"stackHash":"0x…","deploymentId":"0x…","enc":"0x…","ciphertext":"0x…"}` with an `X-Request-Id` header. HPKE base mode, RFC 9180 suite X25519 / HKDF-SHA256 / AES-256-GCM, `info = "sealed/kb-release/v1"`, `aad = nonce`; `enc` (32 bytes) and `ciphertext` (the bare AEAD output) are separate fields. Plaintext is CJSON, with an entry for every app of the stack (possibly empty) and `_gate` always:
```json
{ "diskKey": "0x…32", "secrets": { "crm": { "PG_DATABASE_PASSWORD": "…" }, "_gate": { "GATE_PASSWORD_BCRYPT": "…" } }, "signerSeed": "0x…32" }
```
`diskKey = HMAC_KMS("sealed/disk/v2" || customer[20] || salt[32])`, `signerSeed = HMAC_KMS("sealed/signer/v2" || customer[20] || salt[32])` (D-058, replacing the deploymentId of D-011; `customer` is the bootstrap customer and `salt` the config's), using the bootstrap's Cloud KMS HMAC-SHA256 key version 1 (`macSign`). Both survive reboots and stack upgrades that keep the salt, and never leave KMS in root form. Local dev uses a file-backed HMAC key (dev build only).

Answers other than 200 are `{"decision":"denied"|"error","reason":"<code>","detail":"…"}`: 403 `denied` with the denial reasons above; 400 `bad_request` (malformed body, unusable ephemeral key); 413 `bad_request` (body over 2 MiB); 429 `rate_limited` with `Retry-After: 2` (per-client limit, parse queue or release slots full); 503 with `Retry-After` for `chain_stale` (5 s); 503 `unavailable` (RPC, catalog, Intel PCS, Secret Manager, KMS, the 90 s release deadline); 503 `secret_missing` or `secret_invalid` (a required manifest secret is not stored or not usable; the customer fixes it with `sealed secrets set` and the agent retries); 503 `decision_log_unavailable` (an allowed release is withheld when its Cloud Logging write fails); 500 `internal` (a defect in the broker).

Secret Manager naming: `sealed-<appId>-<NAME>` (for example `sealed-crm-PG_DATABASE_PASSWORD`) and `sealed-gate-password`, which holds the bcrypt hash of the gate password and is released unchanged as `_gate/GATE_PASSWORD_BCRYPT` (a value that is not a bcrypt hash is refused). The broker reads only secrets named in the manifests of the stack's releases; missing optional ones are left out. A manifest secret with `same_as: "<appId>/<NAME>"` (D-043) is read from `sealed-<appId>-<NAME>` and released under the referencing app's name, only when the referenced app is in the stack, declares that secret itself (not as a reference), lists the referencing app in that secret's `share_with` (D-059), and is not optional while the reference is required. The broker reads `same_as` and `share_with` from the raw manifest, and `Compose` enforces the same rules.

Shared spend budget (D-048): fee settlement and the payer draw on one limit. In `access-key` mode it is the access key's onchain authorization: the agent reads the key's remaining fee-token limit and period end (at boot, after every settlement, and when a reservation finds the reading over 60 s old), and the payer may reserve at most `remaining - spent since the read started - open reservations - reserved_for_fees`; any period is followed as authorized and `settlement.spendLimitPerDay` is not used. Before the first read, and for a missing, revoked or expired key, the payer gets nothing. In `enclave-account` mode, and for a key without limits, the limit is `settlement.spendLimitPerDay` per UTC day: `limit - fees spent - payer spent - open reservations - reserved_for_fees`. reserved_for_fees covers the whole window (the onchain period, else the UTC day): unpaid legs (except the ones counted in `unpayableLegs`), the open period, app-hours until the window ends, 0.01 USD of network fees per app transaction of the next settlement, and the later settlements' transactions at twice the last network fee seen. In access-key mode the chain enforces the limit and the budget never refuses settlement; in `enclave-account` mode nothing onchain limits fees, so the agent caps settlement at `limit - spent - open reservations` and fees beyond it fail with `spend_limit` (review I6). At most 64 reservations are open; one not released within 15 minutes counts as spent until a late release corrects it, and open reservations survive the window roll. A reservation is saved on the encrypted disk before its id is returned (503 if the save fails). The payer reserves before each debit with `currency` = FEE_TOKEN, treats `ok:false` as a refusal (429 to its caller), treats 400, 401, 403, 404, 422, 5xx and timeouts as unavailable and refuses to pay (503 `spend_budget_unavailable`), releases with `used` (`"0"` when the payment never left or the relay answered 402), treats 404 on release as already released, and keeps its local SpendGuard over the whole daily limit as a second cap.

Settlement (spec 7.3, D-062, D-073). Every settlement interval the agent first rebuilds its paid ledger from the platform's stored reports (section 10, signed read) and onchain `usagePaid`, then cuts and signs the period's report (never one whose period starts before the latest period it knows was signed), saves it, posts it to `POST /v1/usage`, and pays only reports the platform accepted. A 409 that names another stored report voids the cut report (never paid, never sent again). Failures on the customer's side (`access_key_missing`, `access_key_revoked`, `access_key_expired`, `spend_limit`, `insufficient_balance`, `tx_failed`, `tx_unconfirmed`, `estimate_reverted`, `leg_token_mismatch`, `not_in_deployment`, and `rpc_error`, because the customer chooses the RPC and controls the VPC firewall) start the grace period (`settlement.gracePeriodMinutes`, 24 h by default), also when the platform is down at the same tick; after it Caddy loads the payment-needed Caddyfile (section 14), and a Closed deployment (`deployment_closed`) switches at once. Failures on the platform's side (`PLATFORM_SIDE_FAILURES` in `runtime/agent/src/payments/settler.ts`: `ledger_unverified`, the stored reports could not be read in this boot; `usage_not_submitted`, the platform has not accepted a report; `deployment_not_registered`, the oracle has not registered the deployment from the agent's evidence yet), when nothing on the customer's side failed in the same settlement, defer it instead (D-073): the health report carries `deferredSince`, nothing that waits on them is paid (reports the platform accepted before the outage are), the grace period does not run (a running one is paused and resumes where it stopped), and the deferred fees are paid once the platform is back. A deferred tick that pays every leg it tries ends a customer-side failure streak, so a customer who fixed their side during an outage leaves the payment-needed page at once. The FeeSplitter daily cap and legs above a lowered per-payment cap (`overCap`) are deferrals, not failures. `lastOutcome` in the health report carries the content-free reason.

Callers without an allowlist stay in the config, so traffic from those addresses is counted under a name. Endpoint hosts become `host:port` (443 unless the URL names a port). Service names are at most 57 characters and contain no `--`. `statsReaders` is `172.30.0.3`, `upstreamDns` `8.8.8.8:53` and `8.8.4.4:53`, `allowedPrivateCidrs` the config's `allowedVpcRanges`. sealed-egress listens on every network it joins.

- `callers[].proxyAuth` (optional, only ever `true`) makes the caller also present a proxy credential; the composer does not set it (identity is the source address, NET_RAW is dropped on app services and app networks are separate).
- Matching: exact `host:port` or `*.domain:port` (exactly one extra label). Hosts lowercase ASCII, at least two labels; ICANN public-suffix wildcards and IPv6 literals are rejected. CONNECT and absolute-URI `http://` proxying; absolute `https://` and client-chosen upstream proxies are refused.
- Destination IP checks after resolution and again before the dial (only the checked IP is dialed): always deny metadata (169.254.169.254 and the IPv6 metadata addresses), loopback, link-local, 0/8, multicast, reserved, special-use and NAT64 ranges, the VM ranges `172.30.0.0/16` and `172.31.0.0/24` (`policy.VMInternalPrefixes`, equal to the composer's `VMRanges`, bridge gateways included; counted as `ip-vm-internal`, D-064) and the networks of egress's own interfaces; private ranges (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7) only inside `allowedPrivateCidrs`, and `allowedPrivateCidrs` may not lie inside the VM ranges. Raw-IP destinations are denied unless an allow entry is that IP. Denials are 403 with `X-Sealed-Egress: blocked`; 429 with `X-Sealed-Egress: limited` over a per-caller limit.
- DNS: A/AAAA only for names on the caller's allowlist (denied addresses stripped); other types for allowed names NOERROR without records; ANY or non-IN class REFUSED; other names NXDOMAIN; unknown sources and rate-limited queries REFUSED; all counted.
- Stats: `GET /v1/stats` (only from `statsReaders`) -> `{"since","allowed":{"<key>":n},"blocked":{"<key>":n},"callers":{"<name>":{"allowed","blocked"}}}`, where keys are allowlist entries or words of a fixed vocabulary (`unlisted:<port>`, `ip-<class>:<port>`, `invalid:<port>`, `rate-limited:0|53`, `unauthenticated:0`, `other:0`), never a name or address a container chose. `<port>` is the requested port when it is 80, 443 or a port the caller's allowlist lists, else `other`; `ip-<class>` is one of `ip-public`, `ip-private`, `ip-metadata`, `ip-loopback`, `ip-link-local`, `ip-vm-internal`, `ip-reserved`, `ip-multicast`, `ip-unspecified`, `ip-ipv4-embedding`. Every count served is rounded down to two significant figures (`stats.RoundDown2`, aggregates summed exactly first, D-065); the in-VM counters and the log stay exact. `GET /healthz` for anyone. Counts are logged once a minute; never paths or payloads.
- sealed-egress runs with `net.ipv4.ip_forward=0` (section 6, D-064), so it never routes packets between its networks.

## 14. App fragments and in-VM runtime conventions

Manifest (`manifest.yaml`, `catalog/schema/manifest.schema.json`): `schema`, `id`, `name`, `category`, `description`, `release_version`, `upstream`, `maintainer`, `maintainer_share_bps`, `compose_fragment` (`compose.fragment.yaml`), `egress_policy` (`egress.yaml`), `primary_service`, `images` (`name`, `source`, `digest`, `platform`, `license_spdx`, `ref` written only by the bundle builder), `resources`, `routes`, `healthcheck`, `metering`, `secrets`, `telemetry_off_env`, `telemetry_none_reason`, `license_exclusions`, `license_exceptions`, `bootstrap`, `notes`.

- Reserved ids: `sealed`, `sealed-*`, `caddy`, `gate`, `localhost`. `primary_service`, `routes[].service`, `healthcheck.service` and `bootstrap.service` start with `<id>-`.
- Routes: `name`, `service` (must be the `primary_service`, since Caddy is on `apps` only), `internal_port`, `path_or_host` (the route name or a path), `auth` and `on_attest_host`. `auth` is `gate` for every route except llm-gateway's `gateway` (`bearer-passthrough`, LiteLLM keys) and inference-relay's `relay` (`public`, the paid MPP endpoint). `on_attest_host: true` is allowed only for the route named `relay` with a path prefix other than `/attest` (`/v1`): Caddy serves it on the attest host, same origin and certificate as `/attest` (D-045), and it gets no host of its own.
- Secrets: `name`, `description`, `generate`, optional `optional`, `same_as` and `share_with`. Names are at most 128 characters (envexec's limit) and may not be a variable the composer sets (proxy variables, `NODE_USE_ENV_PROXY`, `SEALED_PUBLIC_URL_*`) or a `telemetry_off_env` key. Generators: `none` (the customer supplies it), `hex32` (64 lowercase hex), `base64-32` (32 random bytes, standard base64 with padding), `sk-hex32` (`sk-` plus hex32), `password` (24 characters uniform over `[A-Za-z0-9]`). `GATE_PASSWORD_BCRYPT` is reserved. `same_as: "<appId>/<NAME>"` (D-043) takes the value of another app's secret: it needs `generate: none`, may not name its own app, and composing requires the referenced app in the stack declaring that secret, which may not itself be a reference and must list the referencing app in its `share_with`; a required secret may not reference an optional one. `share_with: [<appId>...]` (D-059) is the source secret's opt-in: unique app ids, not its own app, not on a secret that is itself a `same_as` (llm-gateway's `APP_KEY_CODING_AGENT` declares `share_with: [coding-agent]`). The composer, the key broker and `sealed secrets` all enforce it. The key broker releases the value under the referencing app; `sealed secrets` stores it once, under the referenced app.
- `bootstrap`: optional `service` (gets `restart: on-failure`) and `done_file`, `<volume>/<path>` relative to `/mnt/sealed-data/<appId>/` (the older absolute form under a named-volume mount still resolves, with a lint warning; tmpfs paths are rejected). The gate keeps the app's routes at 503 until it exists.
- `license_exceptions: [{decision, paths, reason}]` are honoured only for decision ids listed in `runtime/composer/lint/exceptions.go` (empty).
- Release versions follow section 7.

`compose.fragment.yaml` is a docker compose snippet with `services:`, `volumes:` and `x-*` anchor blocks only. Rules the composer enforces (violations are errors, with the field named):

- Service names are lowercase DNS labels starting with `<appId>-`, at most 57 characters, without `--`, unique across the stack together with app aliases and sidecar names.
- Allowed service keys: `image` (`{{image:<name>}}` naming a manifest image), `command`, `entrypoint` (required, a list), `environment` (public values only; no host passthrough, no composer-owned keys such as proxy variables, `NODE_USE_ENV_PROXY` or `SEALED_PUBLIC_URL_*`, no secret names), `healthcheck`, `depends_on` (same app only, no cycles), `volumes`, `tmpfs` (`<path>[:size=…,mode=…]`), `user`, `working_dir`, `read_only`, `stop_grace_period`, `shm_size`, `ulimits`, `mem_limit`, `cpus` (integer or quoted decimal), `labels`, `x-sealed-secrets`. Everything else is rejected, including `privileged`, `cap_add`, `devices`, `network_mode`, `networks`, `ports`, `pid`, `ipc`, `security_opt`, `build`, `env_file`, `secrets`, `configs`, `extra_hosts`, `dns`, bind mounts, anonymous volumes and reserved targets (`/run/sealed/…` and `/var/run/sealed/…`, `/run` and `/var/run` themselves, `/sealed` and `/sealed/…`, the dstack socket under either path; review C-8).
- `$NAME` and `${…}` are errors (they would read unmeasured host environment); `$$` is a literal `$`.
- Top-level `volumes`: names only, each empty or `{x-sealed-owner: "<uid>:<gid>"}` (decimal ids below 2^31). Every volume is a directory on the encrypted data disk; the owner is recorded in sealed-stack/v1 and the agent creates the directory with it before the ready flag.

Added by the composer to every app service of app `n`:

- the entrypoint `["/sealed/bin/envexec","--app","<appId>",("--secret"|"--optional-secret",NAME)...,"--",<entrypoint>...]`. envexec (static Go binary, `runtime/envexec`) waits for `/run/sealed/ready/ok`, exports each declared `/run/sealed/secrets/<appId>/<NAME>` as an environment variable (an empty file of an optional secret counts as not set; an empty required one is refused), then execs;
- networks per section 6; `dns: [172.30.<n>.2]`; `HTTP_PROXY`, `HTTPS_PROXY`, `http_proxy`, `https_proxy` = `http://172.30.<n>.2:3128`; `NO_PROXY`/`no_proxy` = every service name and app alias in the stack plus `localhost,127.0.0.1`; `NODE_USE_ENV_PROXY=1`; the manifest's `telemetry_off_env`;
- `SEALED_PUBLIC_URL_<ROUTE>=https://<host>` for every route the app owns (route name upper-cased, `-` as `_`, no trailing slash; the attest host for a route on the attest host);
- one read-only bind per secret it lists in `x-sealed-secrets`, `{type: bind, source: /run/sealed/secrets/<appId>/<NAME>, target: the same path, read_only: true, bind: {create_host_path: false}}`, never a directory (D-042);

- for the manifest healthcheck service without its own healthcheck: `envexec probe http://127.0.0.1:<port><path>`.

sealed-agent contract (before the ready flag): open the data disk; create every `dataDirs` entry (declared owner on every boot, else the first mounting service's numeric `user` at creation), refusing symlinks and paths outside `<dataRoot>/<appId>/`; check that `secretsRoot` is on tmpfs and that `secretFiles` equals the compose's secret binds (each bind's host path equal to its target, no other owner's files, read-only); write every `secretFiles` entry (0444, owner directories 0755): the released value, or an empty file for an optional secret the customer did not set. The gate hash stays in memory. Then create `/run/sealed/ready/ok`. `GET /v1/ready` answers 2xx only after that. The agent then drops to uid and gid 10001.

Caddy (one site per route host plus the attest site; routes longest path first; every handle body is a `route` block):

- `gate` routes: `request_header -X-Sealed-Gate-Set-Cookie` and `-X-Sealed-Gate-Strip-Authorization` (a client cannot supply either); `forward_auth sealed-agent:7070 { uri /v1/gate?route=<route>; copy_headers Set-Cookie>X-Sealed-Gate-Set-Cookie X-Sealed-Gate-Strip-Authorization }`; the copied `Set-Cookie` goes onto the client response and both relay headers are removed; `Authorization` is removed only when it carries the gate's Basic credentials: when the agent's 200 carries `X-Sealed-Gate-Strip-Authorization: 1`, and when it matches `^[Bb][Aa][Ss][Ii][Cc][ \t]+c2VhbGVkO` (base64 of `sealed:`, spaces or tabs, review C-3), so an app's own `Authorization` passes untouched; then `reverse_proxy` with `network_proxy none`.
- `bearer-passthrough`: requests with `Authorization: Bearer …` first lose client copies of `X-Sealed-Gate-Set-Cookie` and `X-Sealed-Gate-Strip-Authorization`, then ask `forward_auth sealed-agent:7070 { uri /v1/gate?route=<route>&bearer=1 }` (the bearer mode below, composer 1.4.0, review C-6), then lose the `sealed_gate` cookie and reach the app with `Authorization` unchanged (nothing copied, nothing stripped); the rest of the route is gated as above. So bearer requests are held with 503 `starting` exactly like gated ones until the keys are released and the app's bootstrap is done (the only such route is llm-gateway `gateway`, where LiteLLM checks every key). The payment-needed variant answers them with a plain 402 and asks nobody. `public`: proxied without a gate.
- The `sealed_gate` cookie is removed from every app request's `Cookie` header.
- The attest site maps `/` and `/attest` to `sealed-agent:7070/attest` keeping the query, serves the `on_attest_host` routes next to it, and answers 404 elsewhere.
- Global options: admin on `unix//run/sealed/caddy-admin/admin.sock|0660`, `persist_config off`, `ocsp_stapling off`, HTTP/1.1 and HTTP/2. ACME goes through sealed-egress.
- Payment-needed variant: every app host answers the static page with 402 (bearer API calls get a plain-text 402), routes on the attest host a plain-text 402, `/attest` unchanged. The agent switches with `POST /load` (`Content-Type: text/caddyfile`) of one of the two measured Caddyfiles over the admin socket (mode 0660, group 10001; no root helper), re-applied every settlement tick.

Gate (D-044), `GET /v1/gate?route=<route>` from Caddy's address only (403 for anyone else) with the client's headers plus `X-Forwarded-Method`, `X-Forwarded-Uri` and `X-Forwarded-For`:

- 200 for a valid `sealed_gate` cookie (`v1.<expiresAt>.<session id>.<base64url HMAC-SHA256>` with a per-boot key over `sealed/gate-cookie/v1|<expiresAt>.<session id>`, route independent, 12 h), or for `Authorization: Basic` (scheme, spaces, credentials) with user `sealed` matching the released bcrypt hash. A Basic success sets `Set-Cookie: sealed_gate=…; Path=/; Max-Age=43200; HttpOnly; Secure; SameSite=Lax`. 200 answers carry `X-Sealed-Gate: cookie|basic|bearer`, and `X-Sealed-Gate-Strip-Authorization: 1` when the request's `Authorization` held Basic credentials for user `sealed`.
- 303 instead of 200 for a Basic success on a browser navigation (`X-Forwarded-Method: GET`, `Sec-Fetch-Mode: navigate`), `Location` the same-origin path and query, with the `Set-Cookie`.
- 401 with `WWW-Authenticate: Basic realm="sealed"` otherwise.
- 503 `starting` until the hash is released and the route's app's bootstrap is done (`bootstrap.donePath` exists as a regular file, or the job reported `POST /v1/bootstrap/done`); 503 `gate not configured` when the hash is not bcrypt or its cost is above 20; 503 `busy` when the bcrypt worker's queue is full. 503 answers carry `Retry-After: 5`.
- 429 with `Retry-After` for repeated failures per client (burst 10, one per 6 s; IPv6 clients per /64) or, for clients with a failure in the last 10 minutes, overall (burst 30, one per second). bcrypt runs in a worker; a successful Basic check is remembered for 5 minutes.
- Bearer mode (review C-6): `GET /v1/gate?route=<route>&bearer=1` asks only whether a `bearer-passthrough` route is open: 403 for a route without bearer passthrough, 503 `starting` before the keys are released or while the app's bootstrap runs, then 200 `X-Sealed-Gate: bearer` for a request with `Authorization: Bearer <token>` (the app checks the token) and 401 otherwise. Composer 1.4.0's bearer-passthrough handles call it for every bearer request.

Metering: manifest `metering.source: heartbeat` apps get app-hour accounting from the agent's health polling of the healthcheck service (by its app-network address); `callback` apps post to `http://sealed-agent:7070/v1/usage-events`.

## 15. Dev simulator, payer key, host rules

Simulated quotes (dev only, never accepted by production builds): bytes are ASCII `SEALEDSIM1` followed by CJSON `{"schema":"sealed-sim-quote/v1","mrtd":"<hex48>","rtmr0":"…","rtmr1":"…","rtmr2":"…","rtmr3":"<hex48>","reportData":"<hex64>","debug":false}`. Fixed sim measurements: mrtd = 48 x `0x11`, rtmr0 = 48 x `0x22`, rtmr1 = 48 x `0x33`, rtmr2 = 48 x `0x44` (debug variant: same but `"debug":true` and mrtd = 48 x `0x55`). These are registered as images `sealed-sim` / `sealed-sim-debug` on local chains only.

The simulator (`runtime/agent/sim`) serves the dstack guest-agent subset over a unix socket or TCP (`DSTACK_SIMULATOR_ENDPOINT`): `POST /GetQuote {"report_data":"<hex<=128>"}` -> `{"quote":"<hex>","event_log":"<JSON string>","report_data":"<hex128>","vm_config":"{}"}` and `GET /Info`. It reads an app-compose.json file, emits the exact RTMR3 event sequence of section 6 for it, and sets rtmr3 to the replayed value. The event log is a JSON array of `{"imr":3,"event_type":134217729,"digest":"<hex48>","event":"<name>","event_payload":"<hex>"}` exactly like dstack (RTMR0-2 entries omitted in sim).

Payer key: sealed-agent writes the enclave signer private key to `/run/sealed/secrets/sealed-mpp-payer/ENCLAVE_KEY` and the daily limit to `/run/sealed/secrets/sealed-mpp-payer/SPEND_LIMIT_PER_DAY`; only sealed-mpp-payer binds those two files (`SEALED_SECRETS_DIR=/run/sealed/secrets/sealed-mpp-payer`, `SEALED_AGENT_URL=http://sealed-agent:7070`, `SEALED_VERIFIERD_URL=http://sealed-verifierd:8088`). In access-key mode the payer signs as an access key of the customer account (`Account.fromSecp256k1(key, { access: customer })`). It pays the relay only in `config.feeToken` (required) and refuses to start with the removed `RELAY_SPEND_SHARE_BPS`.

Payer API and state (`runtime/mpp-payer`, port 8090). `GET /healthz` -> `{"ok":true,"relayAttested","sessions"}`. `/v1/*` serves only llm-gateway's addresses (`ALLOWED_CALLERS`, resolved by name; 403 `forbidden_caller` otherwise); `GET /v1/models` and `POST /v1/chat/completions` (OpenAI-compatible, at most 4 MiB, the relay's own limit) pass the relay attestation gate before any payment. Errors are `{"error":{"type","message"}}`:

| status | type | meaning for the caller |
|---|---|---|
| 400 | `invalid_request` | the body is not a JSON object |
| 413 | `request_too_large` | body over 4 MiB |
| 429 | `spend_limit_exceeded` | the shared budget or the local SpendGuard refused; unpaid, a later retry is free |
| 503 | `relay_attestation_failed`, `spend_budget_unavailable` | the relay is not attested (or presented another TLS key), or the agent's budget could not be reached; unpaid |
| 424 | `relay_failed_after_payment` | the relay took a per-request charge and then failed (`relay_status` when it answered); paid, do not retry: LiteLLM and the OpenAI SDKs retry 429 and 5xx, so this is a 4xx they do not retry |
| 502 | `relay_session_failed` | the session request failed after it was sent |
| 502 | `payment_refused`, `relay_unreachable`, `relay_stream_failed` | the payment firewall refused the relay's challenge, or the relay could not be reached or failed before anything was paid |

A per-request charge is always sent as a stream; a non-streaming caller gets it folded back into one `chat.completion`. The payment firewall accepts only `tempo` challenges on an allowed chain, in `config.feeToken`, to the payee the relay attestation proved (the treasury); charges are pull mode (a signed transaction of `transfer` or `transferWithMemo` to the payee for exactly the challenge amount, at most `MAX_CHARGE`), a `proof` credential only for a zero-amount charge (mppx's session bootstrap), and sessions only over the TIP-1034 escrow precompile with that payee and token (D-054a). State lives in `STATE_DIR` (default `/var/lib/sealed-mpp-payer`): `spend-state.json` (the SpendGuard's day), `channels.json` (the channel journal) and `session-store.json` (the mppx session store). Since composer 1.4.0 that directory is the data-disk bind `/mnt/sealed-data/_mpp-payer/state` (section 14), owned by the payer's uid 1000 and made 0700 by `envexec private`, so the state survives image updates, stack upgrades on the same data disk (D-058) and VM replacement, not only restarts.

Relay (`runtime/relay`, inference-relay's `relay` route on its attest host, D-045). Prices per model, `max_tokens` bounded by the model's limit, request bodies at most 4 MiB. Sessions (TIP-1034 escrow, per-token vouchers) and per-request charges (`tempo` charge, pull mode only). A per-request charge is deferred: the relay validates the credential without broadcasting it, calls the upstream, and settles the charge only after the upstream answered 2xx and produced its first byte, at least 6 s before the payer's transaction expires (`validBefore`; 20 s without one). An upstream that fails or stays silent before that costs nothing: the answer carries no payment receipt, `charged: false` and `upstream_status` when there was one (`upstream_timeout` 504, `upstream_error` with the upstream's status, `charge_failed` 502 when settling failed), and the signed transaction expires unbroadcast. A provider whose own attestation does not verify answers 503 `attestation_failed` (`provider_unavailable` for a provider that is not enabled) before any payment.

Host rules (v3, `runtime/composer/hostrules.go`): `pre_launch_script` rebuilds two chains on every boot and inserts each jump once, verified with `-C`:

- `SEALED-EDGE` (ESTABLISHED,RELATED return; source `172.31.0.2`, sealed-egress, return; destination inside the edge subnet return; everything else drop), jumped from the top of `FORWARD` and, when the `DOCKER-USER` chain exists (Docker's iptables backend), from the top of `DOCKER-USER`, both with `-i sealed-edge` and with `-s 172.31.0.0/24`, so a packet an edge member forwards with another source cannot bypass it (review ws-int-agent 4).
- `SEALED-INPUT` (D-064; ESTABLISHED,RELATED return, everything else drop), jumped from the top of `INPUT` with `-s 172.30.0.0/16`, `-s 172.31.0.0/24` and `-i sealed-+` (every composer bridge). Containers then reach no listener of the VM itself (the dstack guest agent's `0.0.0.0:8090`, anything else) through their bridge gateway. The stack needs nothing on `INPUT`: Docker's embedded DNS answers inside each container's namespace and forwards to sealed-egress from there, published ports arrive through DNAT and `FORWARD`, and container traffic is bridged.

The script runs under `set -euo pipefail` and fails closed: it exits non-zero when a chain or a jump cannot be verified, or when `DOCKER-USER` exists but `FORWARD` does not jump to it. It is fixed text rendered by the composer (only the edge subnet, the egress IP, the edge bridge, the container ranges `VMRanges` and the bridge pattern vary) and part of stackHash (golden: `runtime/composer/testdata/golden/pre-launch.sh`).

## 16. Customer bootstrap and the CLI

`sealed bootstrap` (alias `sealed connect gcp`, D-032) applies `infra/terraform/customer-bootstrap` (embedded in the CLI) in the customer's project with the customer's own token. It creates the key broker on Cloud Run (image pinned by digest, `ghcr.io/sealedtempo/sealed-key-broker` from `catalog/tools/release/extra-images.json`, pulled through the project's Artifact Registry remote repository `sealed-ghcr`; max instances 1, ingress all, unauthenticated invocations, port 8080), the Cloud KMS HMAC_SHA256 key (version 1, never rotated or destroyed), the deployer service account (only the platform service account may mint tokens for it), the boot bucket, and the `sealed` network with its firewall rules. The key broker's service account gets `roles/secretmanager.secretAccessor` with an IAM condition on names starting `sealed-`, `roles/cloudkms.signer` on that one key (`macSign`) and `roles/logging.logWriter` (its decision log), nothing else.

Key broker environment set by the bootstrap: `SEALED_CUSTOMER_ADDRESS`, `SEALED_GCP_PROJECT`, `SEALED_GCP_PROJECT_NUMBER`, `SEALED_SECRET_PREFIX` (`sealed-`), `SEALED_KMS_KEY_VERSION` (the key's `cryptoKeyVersions/1` resource name), `TEMPO_RPC_URL`, `TEMPO_CHAIN_ID`, `SEALED_PLATFORM_REGISTRY`, `SEALED_APP_REGISTRY`, `SEALED_DEPLOYMENT_REGISTRY`, `SEALED_RELEASE_ASSET_BASE` (the bootstrap module's map, `infra/terraform/customer-bootstrap/modules/key-broker-env`, which tests keep equal to the broker's own list). Set by the bootstrap only when chosen (`bootstrapOptionalEnv`, Terraform `fee_splitter`, `fee_token` and `key_broker_allowed_images`, CLI `--fee-splitter`, `--fee-token` and `--allowed-images`): `SEALED_FEE_SPLITTER` and `SEALED_FEE_TOKEN` (mainnet's by default; `sealed bootstrap` takes them from a deployments file of another chain and stops when that file has none) and `SEALED_ALLOWED_IMAGES`. A production broker image serves only chain 4217 (D-060), so `sealed bootstrap` warns for another chain. Optional tunables the bootstrap does not set: `SEALED_GCP_REGION`, `SEALED_DECISION_LOG_ID`, `SEALED_TCB_ALLOWED`, `SEALED_TCB_ADVISORIES`, `SEALED_MAX_IN_FLIGHT`, `SEALED_NONCE_CAPACITY`, and the Google API endpoint overrides. The broker refuses to start with any other `SEALED_*` or `TEMPO_*` variable (a dev build with `SEALED_DEV_SIM=1` only warns), and its endpoints must be https (plain http only to loopback). Runtime settings, not broker configuration: 1 GiB of memory with `GOMEMLIMIT=768MiB`, request concurrency 80 (the broker bounds its own work: 4 body parses and 8 release slots at a time; 80 bodies of 2 MiB stay below half of `GOMEMLIMIT`) and a 120 s request timeout, above the broker's longest request, `keybroker.MaxRequestDuration` (10 s body read, 90 s release deadline and 15 s decision log write, 115 s; `TestBootstrapCloudRunLimits`).

The bootstrap's output is the connection token `sct_` + base64url(JSON) with `v`, `project`, `region`, `deployerAccount`, `keyBrokerUrl`, `customer`, `subnetwork` and `issuedAt`. It holds no secret.

`sealed secrets` writes Secret Manager entries `sealed-<appId>-<NAME>` without a trailing newline, with the manifest generators (section 14), and `sealed-gate-password` as the bcrypt hash (cost 12) of the gate password; an existing secret is replaced only with `--rotate`. A `same_as` secret is stored once, under the referenced app.

Stack file (`sealed-deploy/v1`, `cli/examples/stack.yaml`): `name` (resources `sealed-<name>`, `sealed-<name>-data`, `sealed-<name>-ip`), `connection` (an `sct_` token) or `project`, `region`, `keyBroker`, `customer`; optional `zone`, `machineType`, `dataDiskGb`, `bootBucket` and `salt` (default `0x` + `sha256("sealed/deploy-salt/v1" || 0x00 || project || 0x00 || name)`, so a redeploy keeps its deploymentId); `image` (`id`, `boot`, `systemDisk`, `vmConfig`); `apps` (`id`, `release`: `latest`, a version or a releaseId); `egressAdditions`; `endpoints` (`platformApi`, `relay`, `relayAttest`); `relayOwner`. `sealed deploy` composes with runtime/composer from onchain releases and stops with exit 3, printing the `approveStack` arguments, until the customer's wallet has approved exactly that stackHash. Deploy labels the data disk `sealed-disk-id` (the first 20 bytes of `sha256("sealed/data-disk/v1\0" || customer || "\0" || salt)`, nothing secret) and `sealed-variant`, and refuses a disk created for another wallet or salt; `--replace` upgrades a running deployment on the same data disk and IP (D-058). A debug image (`image.debug: true`, PlatformRegistry `isDebug`) gets the bootstrap's optional `sealed-debug-logs` account with only the `logging.write` scope, the one exception to "no service account", and never a production deployment's data disk.
